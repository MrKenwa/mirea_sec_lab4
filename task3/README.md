# Задание 3. Защищённая форма входа

Учебная система авторизации на Go 1.25+ с SQLite и Argon2id.

## Команды

```sh
cd /Users/maxim/study/beza/pr4/task3

# Запуск сервера: база и пользователь создаются автоматически
go run .

# Разблокировка admin; сервер можно не останавливать
go run . unlock

# Сборка и запуск бинарника
go build -o protectedauth .
./protectedauth

# Проверки
go test -race ./...
go vet ./...
```

Остановка сервера — **Ctrl+C**.

Форма: [http://127.0.0.1:4281/vulnerabilities/brute/](http://127.0.0.1:4281/vulnerabilities/brute/).
Логин — **admin**, пароль — **1234**; заданы в `internal/app/bootstrap.go`.
Существующая запись при запуске не перезаписывается.

Адрес фиксирован: `127.0.0.1:4281`. База — `data/auth.sqlite3` относительно
каталога запуска. Запуск и разблокировку выполняй из папки `task3`.
Флагов настройки и команды `serve` нет.

## Общие фичи

- HTML-форма входа, личный кабинет `/protected/` и выход `/logout/`.
- GET-протокол из условия задания:

  ```text
  /vulnerabilities/brute/?username=USER&password=PASS&user_token=TOKEN&Login=Login
  ```

- SQLite хранит пользователей, соли, хеши паролей, блокировки и лимиты IP.
- Сессии находятся в памяти и живут 15 минут; после входа идентификатор меняется,
  после выхода сессия удаляется. Доступ к кабинету проверяется на сервере.
- Отдельные слои: HTTP-обработчики, сервис авторизации, сессии и SQLite-репозиторий.

## Как защищена форма входа

- **Блокировка учётной записи:** после пяти неверных паролей вход закрывается
  до команды `unlock`. Смена IP, cookie и перезапуск сервера её не снимают.
- **Лимит IP:** максимум 20 запросов с параметрами к проверке входа за минуту.
  После лимита — HTTP 429 с `Retry-After`; неверные токены тоже учитываются.
- **Одноразовый токен:** выдаётся в HTML-форме, привязан к сессии и действует
  5 минут. Погашается до проверки пароля. Защищает от CSRF и повторного
  использования запроса; для следующей попытки нужно получить новую форму.
- **Argon2id с индивидуальной солью:** открытые пароли в SQLite не сохраняются.
- **Транзакции SQLite:** проверка пароля и обновление счётчика атомарны,
  поэтому параллельные запросы не обходят порог блокировки.
- **SQL-инъекция и XSS:** SQL использует параметры `?`, HTML — экранирование
  через `html/template`. Параметры запроса и их длины проверяются.
- **Сессии и ответы:** cookie имеет `HttpOnly` и `SameSite=Strict`; установлены
  `no-store`, `no-referrer` и CSP. Технические ошибки клиенту не раскрываются.

Основная защита от полного перебора — блокировка учётной записи. Получение
новых токенов можно автоматизировать; случайно угадать пароль за разрешённые
попытки всё ещё возможно.

GET сохранён по условию задания: пароль остаётся в URL и может попасть
в историю браузера. Сервер предназначен для локальной учебной работы.
